# i18n — traduction des templates

Statut : **implémenté**. Voir [spec-v1.md §5](spec-v1.md) — c'était l'un des
deux points explicitement listés "hors scope v1", avec le [PDF](#voir-aussi).

## Principe

Le français est la langue **source** de tout le projet ([CLAUDE.md](../CLAUDE.md)
— commentaires et UI en français). Un catalogue de traduction ne mappe donc
jamais un identifiant abstrait vers un texte (`"login.title"` → `"Connexion"`),
mais littéralement le texte source lui-même vers sa traduction — convention
gettext (`msgid` = le texte) :

```json
{ "Se connecter": "Log in" }
```

Avantage direct : aucune double maintenance de clés artificielles, et un
texte qui n'a pas encore de traduction reste lisible tel quel (en français)
plutôt que d'afficher une clé technique ou un vide.

## Deux façons de marquer du texte traduisible

**1. Texte statique d'un élément — `t-tr`** (le cas courant), directive du
compilateur ([`xweb/engine/compiler.py`](../xweb/engine/compiler.py)),
même tier de précédence que `t-esc`/`t-out`, ignore les enfants de
l'élément comme eux :

```xml
<h1 t-tr="1">Organisation</h1>
```

Le texte source est normalisé (`_normalize_ws` — espaces/retours à la ligne
internes réduits à un seul espace) avant d'être utilisé comme clé, pour
qu'un bloc de template indenté sur plusieurs lignes n'exige pas une clé de
catalogue qui matche exactement les espaces de mise en forme XML.

**2. Valeur composée à l'exécution — `_()`**, injectée dans le contexte de
rendu (jamais importée par le compilateur lui-même) :

```xml
<t t-esc="_('Bonjour ' + name)"/>
<t t-call="xweb.field" t-att-label="_('Email')" for_="email"/>
```

**Piège confirmé pour de vrai** : `t-tr` posé directement sur un élément
qui porte AUSSI `t-call` n'a **aucun effet** —

```xml
<!-- NE TRADUIT RIEN, silencieusement : -->
<t t-call="xweb.button" type="submit" t-tr="1">Se connecter</t>

<!-- correct — imbriquer t-tr À L'INTÉRIEUR du t-call : -->
<t t-call="xweb.button" type="submit"><t t-tr="1">Se connecter</t></t>
```

`_render_element_body` ([`xweb/engine/compiler.py`](../xweb/engine/compiler.py))
délègue à `_render_call` et retourne dès qu'un `t-call` est présent —
avant même de lire `t-tr` sur cet élément. `_render_call` capture ensuite
les enfants **bruts** de l'élément comme `slot` ; ce n'est pas un cas
particulier de `t-tr`, aucune directive de contenu (`t-esc`/`t-out`/`t-tr`)
ne s'applique sur l'élément porteur d'un `t-call` — le slot est toujours
la copie textuelle des enfants. Un `<t t-tr="1">` **imbriqué** dans le
corps du `t-call`, en revanche, est un enfant normal, rendu par
`_render_children` avec le contexte de l'appelant (qui contient `_`) —
donc traduit correctement. Trouvé en vérifiant pour de vrai l'export
anglais du parcours de connexion (`?lang=en` sur `/plugins/account/login`
ne traduisait pas le bouton "Se connecter") — les ~12 occurrences dans
`plugins/account/templates/` ont toutes ce correctif ; voir
`tests/test_compiler.py::test_t_tr_on_the_same_element_as_t_call_is_a_no_op_documented_trap`
et le test suivant pour la forme correcte.

Convention établie dans ce repo : les composants génériques `xweb.*`
(`field`, `button`, `card`, `stat`…) n'appellent **jamais** `_()` en
interne — ils sont partagés par tous les plugins, pas seulement ceux
traduits. C'est l'appelant qui traduit la prop avant de l'injecter
(`t-att-label="_('Email')"`), et qui doit forwarder `_` explicitement à
tout `t-call` qui en a besoin plus bas (`t-att-_="_"`) puisque `t-call`
isole son contexte — rien n'est hérité automatiquement de l'appelant, voir
[language.md](language.md) sur `t-call`.

`_` réalise toujours un **fallback silencieux** vers le texte source si la
locale résolue n'a pas d'entrée pour ce texte, ou si la locale demandée
n'existe pas du tout : jamais une `KeyError` qui ferait planter une page
entière pour une seule chaîne pas encore traduite. C'est délibéré et
symétrique avec le reste de xweb (conflit XPath, permission→rôle inconnu,
icône inconnue…) — voir la docstring de [`xweb/i18n.py`](../xweb/i18n.py).

## `Catalog` — chargement

`xweb.i18n.Catalog(locales_dir, locales)` charge `<locales_dir>/<code>.json`
pour chaque code de `locales` (le français `SOURCE_LOCALE` n'a besoin
d'aucun fichier — `_()` y est l'identité). Dégradation systématique plutôt
qu'un boot qui plante :

- fichier absent → warning loggé, catalogue vide pour ce code (tout retombe
  sur le français) ;
- JSON invalide ou pas un objet plat → warning loggé, même dégradation ;
- une clé qui commence par `_` (ex. `"_comment"`, convention JSON courante
  pour une note de fichier) est ignorée — aucun texte source français ne
  commence jamais par `_`, donc ça ne fait perdre aucune vraie traduction.

Câblé dans `XwebExtension.init()` ([`xweb/engine/integration/xcore.py`](../xweb/engine/integration/xcore.py))
via deux clés de config sous `services.extensions.xweb.config` dans
[`integration.yaml`](../integration.yaml) :

```yaml
config:
  locales_dir: "locales"
  locales: ["en"]
```

**Piège --reload** : `xcli manager start --reload` passe un `--reload` nu à
uvicorn, qui ne surveille par défaut que les fichiers `*.py` — une
modification de `integration.yaml` (comme l'ajout de `locales_dir`) ne
déclenche **pas** de redémarrage. Il faut relancer le serveur à la main
après tout changement de config YAML pour que `Catalog` soit rechargé avec
la nouvelle liste de locales.

## Résolution de la locale — `resolve_locale`

Ordre de priorité (`xweb/i18n.py::resolve_locale`) :

1. `?lang=` explicite dans l'URL ;
2. cookie `xweb_locale` (posé par `xweb.locale_switcher`, symétrique du
   cookie de thème) ;
3. en-tête `Accept-Language` du navigateur ;
4. `SOURCE_LOCALE` ("fr") par défaut.

Ne retourne jamais un code absent de `catalog.available` — une locale
demandée sans catalogue chargé (ex. `?lang=de` alors que seul `en` est
configuré) retombe sur le français plutôt que d'afficher une page à moitié
traduite.

## Câblage dans `mount.py`

`_resolve_translator(plugin_ctx, request)` ([`xweb/mount.py`](../xweb/mount.py))
récupère `ext.xweb.i18n`, résout la locale, et pose dans le contexte de
rendu de base :

```python
ctx["locale"]   # code résolu, ex. "en"
ctx["locales"]  # catalog.available, ex. ["fr", "en"]
ctx["_"]        # fonction de traduction liée à cette locale
```

Même dégradation gracieuse que le reste de `mount.py` (à la manière du
token CSRF) : si `ext.xweb` ou `i18n` est indisponible, repli sur
`(SOURCE_LOCALE, identité, [SOURCE_LOCALE])` plutôt qu'une exception.

`render_xweb_template()` pose ensuite le cookie `xweb_locale` (durée 365
jours) via `_set_locale_cookie_if_requested`, **uniquement** quand `?lang=`
était explicitement présent dans la requête et correspond à la locale
effectivement résolue (jamais pour un `?lang=de` retombé sur le français —
voir `test_unknown_lang_query_param_does_not_set_a_cookie`).

## `xweb.locale_switcher`

Composant ([`xweb/components/layout.xml`](../xweb/components/layout.xml)) — un
dropdown listant `locales`, chaque entrée pointant vers l'URL courante avec
`?lang=<code>` ajouté (`request.url.include_query_params(lang=code)`).
Masqué automatiquement si une seule locale est disponible
(`t-if="locales and locales[1:]"` — le garde vérifie aussi la vérité de
`locales` lui-même, pas seulement `locales[1:]`, parce que `t-default` ne
s'applique que quand la prop est **absente** des args explicites de
l'appelant, jamais quand elle vaut `None` : un appelant qui passe
`locales=None` sans le savoir ne doit pas planter le rendu).

Wiré dans les deux layouts qui portent un topbar : `xweb.shell_minimal`
(écrans d'auth anonymes) et `xweb.shell` (app connectée), toujours juste
avant `xweb.theme_toggle` :

```xml
<t t-call="xweb.locale_switcher" t-att-locale="locale" t-att-locales="locales" t-att-request="request"/>
```

## Périmètre traduit actuellement

- `plugins/account/templates/` — tout le parcours d'authentification
  **anonyme** (login, register, forgot, reset, mfa, tenant, onboarding,
  logout) et les composants partagés `account.auth_card`/`account.flash`
  ([`_shared.xml`](../plugins/account/templates/_shared.xml)).

`locales/en.json` porte la seule traduction fournie (anglais). Le reste de
l'application (profil, sécurité, organisation, admin, `plugins/demo`) reste
en français — ce n'est pas un oubli, une clé absente du catalogue retombe
simplement sur le texte source (voir plus haut), donc étendre la couverture
à un nouvel écran est une extension additive : ajouter `t-tr`/`_()` dans le
template, ajouter les clés correspondantes dans `locales/en.json`, aucune
migration nécessaire.

## Tests

- [`tests/test_compiler.py`](../tests/test_compiler.py) — comportement de
  `t-tr` en isolation (fallback identité, appel du traducteur, échappement,
  normalisation d'espaces, enfants ignorés, nœud vide).
- [`tests/test_i18n.py`](../tests/test_i18n.py) — `Catalog` (chargement,
  dégradation sur fichier absent/invalide/non-objet, clés `_`-préfixées),
  `resolve_locale` (ordre de priorité complet), et le câblage réel dans
  `mount.py` via un cycle ASGI complet (`TestClient`) : rendu par défaut en
  français, `?lang=en` traduit et pose le cookie, le cookie seul suffit à
  garder la traduction sur la requête suivante, une locale inconnue ne pose
  jamais de cookie.
